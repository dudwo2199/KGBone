# KGBone 유니티 런타임 2단계 설계: 제약

작성: 2026-11-17. 상태: 승인 대기. 앞 단계: `2026-11-16-unity-runtime-stage1-design.md`.

## 1. 목적과 이유

에디터에서 쓴 제약 5종(IK, 트랜스폼, 패스, 물리, 슬라이더)을 유니티에서도 **에디터와 같게** 계산한다.
지금(1단계)은 제약이 있는 파일을 제약 없이 재생하고 가져올 때 경고만 한다. 제약을 쓴 캐릭터는 유니티에서 다르게 움직이므로, 이 런타임을 쓸 이유(에디터와 같은 결과)가 깨진다.

게임에는 에디터에 없는 상황이 하나 있다. 캐릭터 GameObject 자체가 움직이거나 회전하는 것이다. 물리 제약이 이 움직임에 반응할지는 **옵션**으로 두고, 기본은 에디터와 같게(반응 없음) 한다(사용자 결정).

## 2. 목표 · 비목표 · 반목표

### 목표 (2단계 완료 조건)
1. 제약 5종과 제약 타임라인 키가 유니티 계산부(`Runtime/Core`, 순수 C# 9)에서 계산되고, KGBone 핵심(Rust)의 결과와 자동 비교 테스트로 같다(오차 1e-3, 1단계와 같은 기준).
2. 제약 적용 순서·활성 판정(스킨 전용 제약 포함)이 핵심(`pose/mod.rs`의 `compute_pose`, `pose/active.rs`)과 같다.
3. 물리는 상태를 이어 가며, 같은 프레임 간격 입력이면 핵심과 같은 결과를 낸다(여러 프레임 연속 정답 비교). 애니메이션의 물리 reset 키, 코드의 `ResetPhysics()`가 동작한다.
4. 컴포넌트에 **월드 움직임 반영** 옵션(이동 0~1, 회전 0~1, 기본 0)이 있다. 0이면 에디터와 정확히 같고, 0보다 크면 GameObject 이동·회전이 물리 질점의 관성으로 들어간다.
5. 지원하게 된 제약은 가져오기 경고에서 빠진다. 아직 지원하지 않는 것(클리핑·시퀀스)은 계속 경고한다.

### 비목표
- 클리핑, 시퀀스, 애니메이션 섞기·전환(트랙), 실행 중 스킨 바꾸기, 코드로 본 덮어쓰기(3단계). 단, 슬라이더가 내부에서 쓰는 "비율·더하기로 애니메이션 적용"은 이번에 계산부에 들어간다(공개 API로 내보내지는 않음).
- 유니티 물리 엔진(Rigidbody 등)과의 연동. 물리 제약은 KGBone 자체 계산만 쓴다.
- 패스 첨부물·바운딩 박스 등을 화면에 그리기(에디터 전용 표시). 패스 첨부물은 계산용으로만 읽는다.

### 반목표
- 제약이 있는 파일이 경고 없이 에디터와 다르게 움직이는 것.
- 월드 움직임 반영 기본값이 0이 아니어서, 아무것도 안 건드렸는데 에디터와 결과가 다른 것.
- 공식 런타임 코드를 참고하는 것(클린룸, CLAUDE.md 1장). 근거는 `docs/FORMAT.md`와 KGBone 핵심 코드뿐.

## 3. 제약 조건
- 1단계 설계 3장의 제약을 그대로 따른다(클린룸, Unity 6 + URP, C# 9, CI에서 유니티 없음).
- 핵심의 계산을 바꾸지 않는다. 이번 단계는 C# 쪽 이식과 정답 확장만 한다. 이식하다 핵심 버그로 보이는 것을 찾으면 C#은 핵심과 같게 옮겨 정답을 통과시키고, 그 내용을 GAPS.md에 적어 보고한다. 고칠지는 사용자 결정(고치면 핵심·정답·C#을 같이 고친다).
- 물리 연속 정답도 오차 1e-3을 지킨다. 프레임이 쌓이며 float 반올림 차이가 커지면 오차를 늘리지 않고, 먼저 C#의 계산 순서·float/double 사용을 핵심과 맞춘다. 그래도 넘으면 비교 프레임 수를 줄이고 그 사실을 GAPS.md에 적는다(설계 판단).
- 정답 파일은 `npm run unity:golden`이 kgbone.wasm으로 만든다. CI가 정답 최신 여부를 검사한다.

## 4. 방법 (Approaches)

| 방법 | 내용 | 결과 |
|---|---|---|
| A. 한 번에 다 옮기기 | 5종 + 키 + 옵션을 한 번에 이식하고 마지막에 한 번 push | 제외. 제약끼리 앞 결과를 이어 쓰므로 정답이 어긋났을 때 원인을 좁히기 어렵다 |
| **B. 세 묶음으로 차례로** | ① IK·트랜스폼·슬라이더 + 제약 키 + 적용 순서 틀 ② 패스 ③ 물리 + 월드 움직임 옵션. 묶음마다 정답 대상 추가 → 테스트 → push → CI 확인 | **채택(사용자 선택).** 어긋남을 묶음 단위로 좁힐 수 있고, 물리처럼 새 정답 방식이 필요한 부분을 따로 다룬다 |
| C. 핵심 wasm을 유니티에서 실행 | Rust 핵심을 그대로 돌림 | 제외. 유니티에 wasm 실행기가 필요하고 플랫폼마다 사정이 다르다(1단계에서 C# 재구현을 정한 이유와 같음) |

## 5. 설계

### 5.1 계산 순서 (핵심과 같게)
셋업 → 애니메이션 적용(본·슬롯·deform·그리기 순서·**제약 키**) → 활성 본 판정 → 월드 계산 → 물리 reset 처리(요청 Reset, 애니메이션 reset 키 구간 `[lastTime, time)`) → **활성 제약을 배열 순서대로 적용**. 각 제약은 바뀐 본과 그 자식의 월드를 다시 계산한다(핵심의 `set_world` + `update_world(…, bi)`).

### 5.2 모델·불러오기 (`Runtime/Core/Model`)
- `constraints` 배열의 5종을 읽는다. 필드와 기본값은 FORMAT.md 3.3과 핵심 `model`을 따른다. formatVersion 0의 따로 있는 `ik`/`transform`/`path`/`physics` 배열은 `order` 순으로 합친다(FORMAT.md 4장, 핵심 `migrate.rs`와 같게).
- 패스 제약용으로 path 첨부물(closed, constantSpeed, vertexCount, vertices, weighted, lengths)을 읽는다. 그리지는 않는다.
- 애니메이션의 제약 타임라인(FORMAT.md 3.7 표: ik, transform, path, physics, slider 값 채널과 physics reset 키)을 읽는다.
- `ConstraintCount`는 경고용으로 남기되, 경고는 "아직 지원하지 않는 제약 종류가 있을 때"만 낸다(묶음이 끝날 때마다 줄어듦, 3묶음 끝에는 제약 경고 없음).

### 5.3 계산부 (`Runtime/Core/Pose`)
- 제약 종류별 계산기를 공통 인터페이스 하나로 묶는다(`IConstraintSolver.Apply(model, index, pose, ctx)`), 파일은 종류별로 나눈다(`IkSolver.cs`, `TransformSolver.cs`, `PathSolver.cs`, `PhysicsSolver.cs`, `SliderSolver.cs`). 핵심 `pose/*.rs`의 같은 이름 파일을 줄 단위로 대응시켜 옮긴다.
- 포즈 상태에 제약마다 현재 값 배열(`constraint_values`와 같은 모양)을 둔다.
- 애니메이션 적용기(`AnimationApplier`)에 비율(alpha)·더하기(additive) 적용과 "자기 자신 제약 키 건너뛰기"를 넣는다. 슬라이더가 쓴다. 기본 재생은 지금처럼 alpha 1, 덮어쓰기.
- 물리 상태는 `SkeletonPoser`가 들고 있다(핵심 `PoseEngine`과 같은 역할). `PoseRequest`에 물리 진행 방법(없음 / 초기화 / dt초 진행)을 더한다.

### 5.4 월드 움직임 반영 (유니티 전용)
- `KGBoneAnimation` 인스펙터: `physicsMoveFactor`(이동 반영, 0~1, 기본 0), `physicsRotateFactor`(회전 반영, 0~1, 기본 0). 코드로도 바꿀 수 있다.
- 매 프레임 GameObject의 이전 대비 위치·회전 변화를 뼈대 좌표(크기·뒤집기 반영)로 바꿔 계산부에 넘긴다. 계산부는 물리 질점의 "이번 프레임 본 이동량"에 `(GameObject 움직임이 그 점을 옮긴 양) × 반영 값`을 더한다. 회전은 질점 위치를 뼈대 원점 기준으로 회전시킨 차이로 계산한다.
- GameObject 움직임은 본 이동량과 똑같이 다룬다(설계 판단): 질점의 "이번 위치"에 더해지므로 `inertia`가 곱해지고, 그 프레임에 진행 단계가 0이면 본 이동량처럼 다음 단계로 미뤄진다.
- 반영 값이 0이면 이 입력은 0이라 계산이 핵심과 비트 단위로 같은 경로를 탄다.
- `ResetPhysics()`: 물리 상태를 비우고 이전 GameObject 위치도 지금 위치로 맞춘다(순간이동 때 튀지 않게). 컴포넌트가 켜질 때·데이터를 다시 가져올 때도 같은 초기화를 한다.

### 5.5 컴포넌트 재생 (`KGBoneAnimation`)
- 플레이 모드: 매 프레임 물리를 `min(0.1, Time.deltaTime)`초 진행한다. 0.1초 상한은 에디터 재생과 같다(`app/src/anim/player.ts`). 유니티 전체 `Time.timeScale`(느린 화면)은 `Time.deltaTime`에 이미 들어 있어 물리도 같이 느려진다. 컴포넌트의 `timeScale`(애니메이션 속도)은 곱하지 않는다(에디터도 재생 속도와 무관하게 실제 프레임 시간을 쓴다).
- 물리를 진행하는 때: 플레이 모드에서 컴포넌트가 켜져 있으면 **항상** 진행한다. `Stop()` 뒤, 반복 아닌 애니메이션이 끝난 뒤, 컴포넌트 `timeScale` 0일 때도 진행해 흔들림이 가라앉고 GameObject 움직임에도 반응한다(사용자 결정). 에디터는 재생을 멈추면 물리도 멈추므로, 이 멈춘 상태의 모습만 에디터와 다르다. 정답 비교는 재생 중 경우만 한다.
- `Play()`로 애니메이션을 바꾸거나 `Stop()`해도 물리를 초기화하지 않는다(에디터도 애니메이션을 바꿀 때 초기화하지 않는다).
- 에디터 모드(플레이 아님): 물리를 진행하지 않는다(에디터의 정지 화면과 같음).
- 본 따라가기(`KGBoneBoneFollower`)는 제약까지 반영된 본 위치를 읽는다.

### 5.6 정답 비교
- `tools/unity-golden.mjs`의 대상에 묶음마다 시험 파일을 더한다.
  - 묶음 ①: `samples/spine43/ik.json`, `transform.json`, 새로 만드는 슬라이더 시험 파일(`tools/gen-samples.mjs`, 본 연결 시점·고정 시점·loop/clamp·additive를 덮음), 제약 키가 든 파일.
  - 묶음 ②: `samples/spine43/path.json`(+ 필요하면 constantSpeed·closed·가중치 경우를 덮는 새 시험 파일).
  - 묶음 ③: `samples/spine43/physics.json`. 물리는 한 엔진으로 **연속 요청**(예: 1/60초씩 N프레임, 중간에 reset 키를 지나는 구간, 불규칙한 dt)을 보내 프레임마다의 결과를 정답으로 저장한다.
- 각 시험 파일이 어떤 제약 옵션을 덮는지 목록으로 남기고, 덮지 못한 옵션이 있으면 시험 파일을 늘린다.
- 월드 움직임 반영(0보다 큰 값)은 에디터 정답이 없으므로 계산부 단위 테스트로 확인한다: 오른쪽 이동 시 끝 질점이 왼쪽으로 처짐, 반영 0.5면 처짐이 1.0의 절반 근처, 0이면 정답과 같음, `ResetPhysics()` 뒤 튐 없음.
- 유니티 EditMode 테스트: 컴포넌트 수준에서 제약 파일 가져오기(경고 없음), 플레이 모드에서 물리 진행, 반영 옵션이 GameObject 이동에 반응함.

## 6. 정한 것 요약
- 사용자 결정: 방법 B(세 묶음), 월드 움직임 반영은 이동·회전 따로 0~1 옵션·기본 0, 애니메이션이 멈춰도 물리는 계속 진행.
- 설계 판단(틀리면 고칠 것): 물리 dt = `min(0.1, Time.deltaTime)`·컴포넌트 `timeScale` 무관 / `Play()`·`Stop()`은 물리 초기화 안 함 / GameObject 움직임은 본 이동량과 같이 `inertia`가 곱해지고 단계 0이면 미뤄짐 / 핵심 버그는 그대로 옮기고 GAPS에 적어 보고 / 물리 정답 오차는 1e-3 유지, 안 되면 프레임 수를 줄이고 기록.
